# Vercel serverless fetch with Google Drive handoff, replacing the routine's direct fetch

We hit a hard blocker in issue #2: the Claude Code cloud routine's sandbox blocks outbound HTTP to `hn.algolia.com` regardless of network policy setting, so the direct-fetch half of ADR-0001's hybrid design can't run inside the routine. We moved the fetch + keyword pre-filter (previously invoked by the routine, per ADR-0001) into a Vercel serverless function instead, since Vercel has no such egress restriction. The function runs on a daily Vercel Cron schedule, writes the result — the Fetch Payload — to Google Drive, then pushes the routine via its API trigger, passing success/failure explicitly in the trigger payload rather than relying on Drive file state. The routine's own cron trigger is removed; the API trigger is now the sole path in. The routine reads the Fetch Payload from Drive via its Google Drive MCP connector — MCP connector traffic routes through Anthropic's backend rather than the sandbox's network boundary, so it isn't subject to the same egress block.

This keeps the fetch + pre-filter logic in one place (Python, in `src/news_assistant/`, now also deployed as a thin Vercel wrapper) rather than duplicating it, and avoids provisioning any paid infrastructure — Vercel Hobby, the Google Drive API, and Gmail via SMTP + an App Password are all free at this volume. We chose SMTP + App Password over the Gmail API for the new email step specifically because the Gmail API's OAuth "Testing" mode issues refresh tokens that expire every 7 days for sensitive scopes like `gmail.send`, which would silently break an unattended daily job; SMTP has no such expiry and needs no Google verification review.

The trade-off: the pipeline now depends on three externally-provisioned pieces (Vercel project, Google OAuth credentials for Drive, a Gmail App Password) instead of one, and a Drive-read failure inside the routine is a new failure mode ADR-0001 didn't have to consider.
